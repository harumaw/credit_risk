# credit_risk

## Проверка за 2 минуты

Два способа: зарегистрироваться самому и добавить тестовую компанию (А) или войти демо-учёткой
и добавить её собственную компанию (Б).

### А. Новый пользователь

1. Зарегистрируйтесь: любые ФИО, email, пароль и ИНН физлица из списка ниже. ИНН у пользователей
   не повторяется — возьмите тот, что ещё никто не занял:

   <!-- registration-inns -->
   `771234560162` `771234560236` `771234560300` `771234560483` `771234560557`
   `771234560620` `771234560701` `771234560878` `771234560941` `771234561046`
   <!-- /registration-inns -->

2. В кабинете «Добавить компанию» → ИНН из таблицы ниже. Руководителем симулятор запишет вас.
3. Подайте заявку (например, 1 млн на 12 мес — для «контрпредложения» возьмите 5 млн) — через
   несколько секунд придёт решение, статусы обновляются сами.

| ИНН | Компания | Что будет |
|---|---|---|
| 9900000017 | ООО «Тест — одобрение» | одобрение (грейд A, долгов нет) |
| 9900000024 | ООО «Тест — контрпредложение» | на выбор: меньшая сумма на тот же срок или вся сумма на срок длиннее |
| 9900000031 | ООО «Тест — мягкий отказ» | отказ: бизнесу 4 месяца, дата, когда подать снова |
| 9900000049 | ООО «Тест — ручной разбор» | ручной разбор: просрочка 45 дней в прошлом |
| 9900000056 | ООО «Тест — банкротство» | отказ без скоринга: процедура банкротства |
| 9900000063 | ООО «Тест — нужна выписка» | ручной разбор: оборотов в нашем банке нет, нужна выписка |

Эти ИНН может добавить любой пользователь; заявки по ним видит только их автор. Упрощение:
симулятор ЕГРЮЛ получает ФИО и ИНН заявителя (`claimant_*`) и для этих ИНН делает его
руководителем; реальный реестр эти параметры игнорирует. Остальные данные компании — копия
профиля персоны (см. «Демо-учётки»). Для любых других ИНН правило прежнее: добавить можно
только компанию, где вы руководитель. Например, ИНН `7701234560` («Северный ветер») новому
пользователю добавить нельзя — будет «Руководитель в реестре — другой человек»: так и должно быть.

## Внешние источники

Все внешние данные приложение получает по HTTP (`src/app/integrations/`, URL — в `local.env.example`).
Сейчас за всеми URL стоит симулятор `src/simulator/` (сервис `simulator`, порт 8100, без БД).
Локально без Docker: `PYTHONPATH=src uvicorn simulator.main:app --port 8100`.

## Тесты

Тесты идут на PostgreSQL 16 — том же, что в проде. Перед прогоном нужен запущенный Postgres:

```bash
docker compose up -d postgres
poetry install
poetry run pytest
```

- База для тестов — `TEST_DATABASE_URL`, по умолчанию `postgresql+asyncpg://app:secret@localhost:5432/app_test`.
  Рабочую базу `app_db` тесты не трогают.
- На каждый прогон `app_test` пересоздаётся и поднимается миграциями (`alembic upgrade head`),
  так что прогон заодно проверяет миграции; `tests/unit/test_schema.py` сверяет схему с моделями.
- Каждый тест идёт в транзакции, которая в конце откатывается, — тесты друг друга не видят.
- Нет Postgres — тесты падают с ошибкой подключения (не пропускаются).

## Скоринг: синтетические данные и модели

- `ml/` — синтетика МСБ (кредитные истории из соседнего проекта scoring_maps + сгенерированный
  бизнес-профиль, 40 тыс. заявок 2023–2025), ноутбук `ml/research.ipynb` (срезы, матрица переходов
  статусов, WoE/IV, 4 скоркарты + GBM, валидация), выгрузка моделей `ml/artifacts/models.json`.
  Как пересобрать — `ml/README.md`, итоги — `docs/model-card.md`.
- Когда какая модель: таблица `scoring_segments` (условия на признаки + priority, первый подошедший
  активный сегмент); у сегмента рабочая модель — `model_versions.status = champion`, иначе запасной `all`.
  Логика — `app.credit.scorecard` / `app.services.scoring`, признаки — `app.credit.features`.
- Загрузка в БД: локально `docker compose exec app python -m app.dataload.synthetic --limit 10000`,
  на сервер — `bash server-load-synthetic.sh` (проверяет место, копирует данные в `~/credit-risk-data`,
  грузит одноразовым контейнером; `LIMIT=40000` — весь датасет, `--models-only` — только модели).

## Заявка и решение (конвейер)

`POST /applications` сохраняет заявку в `submitted` и кладёт задачу в очередь `tasks`. Воркер
(`python -m app.worker`, сервис `worker` в обоих compose) берёт задачу (`FOR UPDATE SKIP LOCKED`) и
проводит заявку: сбор данных из источников → стоп-факторы → признаки → скоринг → лимит DSCR → решение
(`app/services/pipeline.py`, правила — чистые функции в `app/credit/`).

| Персона | Исход | Почему |
|---|---|---|
| ИП Игоря, 1 млн / 12 мес | одобрено | грейд A, долгов нет |
| «Северный ветер», 5 млн / 12 мес | контрпредложение: ≈2,7 млн / 12 мес или 5 млн / 36 мес | платёж не помещается в доход (DSCR ≥ 1,25) |
| «Новый старт» | мягкий отказ + дата, когда подать снова | бизнесу меньше 6 месяцев |
| «Вектор» | ручной разбор | просрочка 45 дней в прошлом |
| «Закат» | отказ без скоринга | банкротство — жёсткий стоп-фактор |
| ИП Анны | ручной разбор | нет оборотов в нашем банке — нужна выписка |

- Отказ и ручной разбор всегда приходят с причинами простыми словами и советом, что делать
  (`app/credit/reasons.py`); при отказе по доходу — альтернативы (другие продукты/сроки).
- Действия клиента: `POST /applications/{id}/accept {offerIndex}` → `sign-code` (код приходит в ответе —
  имитация SMS, живёт 5 минут, после 5 неверных вводов сгорает — нужен новый) → `sign {code}` →
  выдача. Недопустимый переход или истёкшее предложение — 409, каждый переход — в истории.
- Статусы в реальном времени: `GET /applications/{id}/events` (SSE, авторизация заголовком —
  на фронте `fetch` + `ReadableStream`).
- Повтор отправки с тем же `Idempotency-Key` отдаёт ту же заявку — и при одновременном двойном клике.
  Номер заявки — из sequence `loan_application_number_seq` (1001, 1002, …).
- Сбой источника или задачи (после `WORKER_MAX_ATTEMPTS` попыток) — ручной разбор, а не ошибка.
- Модели: в dev-compose грузятся при старте app (`--models-only`); на сервере —
  `bash server-load-synthetic.sh --models-only`. Нет модели — заявка уходит на ручной разбор.
- Паритет признаков с обучением проверяет `tests/api/test_scoring_parity.py`.

## Кабинет администратора `/adminuser`

Внутренний разбор скоринга: все компании (синтетика + клиенты кабинета), разложение балла по признакам,
что сказали бы другие модели, стоп-факторы, строки платёжной дисциплины БКИ, обороты, история скорингов,
пересчёт; модели — бины, баллы, мастер-шкала, калькулятор, правила `scoring_segments`; выборки — случайные
под условия (seed повторяем), «показать все по фильтрам», CSV, решение × факт, чем группа отличается
от одобренных, champion / challenger, стабильность по месяцам.

- Вход — отдельный для сотрудников (`staff_users`, `POST /admin/auth/login`, токен с `kind=staff`):
  клиентский токен в `/admin/*` не принимается, токен сотрудника — в клиентском API.
- Суперпользователь создаётся при старте (`python -m app.seed`) из env: логин `ADMIN_LOGIN` (по умолчанию `ovv`),
  пароль `ADMIN_PASSWORD`. В dev-compose пароль по умолчанию `1234567890@`; на сервере задайте
  `ADMIN_PASSWORD` в `~/credit-risk/.env` — без него администратор не создаётся. Смена пароля в `.env`
  применяется при следующем старте.
- Синтетика оскоривается при загрузке (`app.dataload.synthetic`): `score_results` хранит входы модели,
  сегмент и рекомендацию по матрице (A–B одобрение, C ручной разбор, D–E отказ,
  стоп-фактор → отказ); факт дефолта — из целевой метки синтетики.
- Заявки клиентов попадают в кабинет сами: конвейер пишет в `score_results` вход модели, сегмент, причины
  и итог заявки. Кнопка «Пересчитать» в карточке считает балл заново на сохранённых данных источников
  (тот же расчёт, что в конвейере, без нового запроса к источникам).
